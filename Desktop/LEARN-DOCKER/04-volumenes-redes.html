Módulo 04

Volúmenes y redes

Dos preguntas que todo proyecto real termina haciéndose: ¿dónde viven mis datos cuando el contenedor muere? Y, ¿cómo hago que dos contenedores se hablen entre sí?

04.1 El problema: los contenedores son efímeros

Analogía de la pizarra

El sistema de archivos de un contenedor es como una pizarra blanca: puedes escribir en ella todo lo que quieras mientras está encendido, pero en el momento en que lo eliminas (docker rm), se borra todo. Si tu base de datos guarda sus archivos ahí dentro sin más, cada vez que reconstruyas el contenedor pierdes toda la información. Los volúmenes son la forma de decir "esta parte no se borra con la pizarra".

04.2 Volumes vs. Bind mounts vs. tmpfs

TipoDónde viveCuándo usarlo
VolumeGestionado por Docker, en su propio espacio en discoDatos persistentes de producción (bases de datos, uploads). La opción recomendada por defecto.
Bind mountUna ruta específica de TU máquinaDesarrollo local: montar tu código fuente para ver cambios en vivo sin reconstruir la imagen.
tmpfsSolo en memoria RAM, nunca toca discoDatos temporales sensibles que no deben persistir ni escribirse a disco.

04.3 Comandos de volúmenes

bash
# Crear un volumen gestionado por Docker
docker volume create datos-db

# Listar volúmenes existentes
docker volume ls

# Ver detalles (incluye la ruta real en el host)
docker volume inspect datos-db

# Eliminar un volumen (falla si algún contenedor lo está usando)
docker volume rm datos-db

04.4 Usar volúmenes y bind mounts con -v

bash
# Volume gestionado: Docker decide dónde vive físicamente
docker run -d -v datos-db:/var/lib/mysql --name mi-db mysql

# Bind mount: montas TU carpeta local dentro del contenedor
# útil para desarrollo — editas en tu editor, el contenedor ve el cambio al instante
docker run -d -v $(pwd):/app -p 3000:3000 mi-app-dev

# Sintaxis más explícita y recomendada (--mount)
docker run -d --mount source=datos-db,target=/var/lib/mysql mysql
-v vs. --mount

-v es más corto y compacto; --mount es más explícito y detecta errores de sintaxis antes (por ejemplo, no crea silenciosamente una carpeta si te equivocaste de ruta). Para producción, se recomienda --mount.

04.5 Redes: cómo se hablan los contenedores

Por defecto, cada contenedor está aislado en su propia burbuja de red. Para que dos contenedores se comuniquen (por ejemplo, tu app y su base de datos), necesitan compartir una red Docker.

Analogía del edificio

Crear una red Docker es como poner a dos departamentos del mismo edificio en el mismo piso, con una puerta interna entre ellos. Ambos siguen siendo espacios aislados del resto del edificio, pero pueden llamarse por nombre —dentro de una red Docker, un contenedor puede alcanzar a otro simplemente usando su nombre como si fuera un dominio, sin necesidad de conocer su IP.

Driver de redQué hace
bridgeLa red por defecto en una sola máquina. Los contenedores en la misma red bridge se ven entre sí por nombre.
hostEl contenedor comparte directamente la red del host, sin aislamiento ni mapeo de puertos.
noneSin red en absoluto — aislamiento total.
overlayConecta contenedores entre distintas máquinas físicas (usado en Swarm/clusters).
bash
# Crear una red personalizada
docker network create mi-red

# Levantar la base de datos EN esa red
docker run -d --network mi-red --name db postgres

# Levantar la app en la MISMA red — puede conectarse usando "db" como hostname
docker run -d --network mi-red -p 3000:3000 -e DB_HOST=db mi-app

# Ver qué contenedores están conectados a una red
docker network inspect mi-red
El detalle que sorprende a todos al inicio

Dentro del código de mi-app, la conexión a la base de datos NO usa localhost — usa db, el nombre del contenedor. Docker resuelve ese nombre automáticamente vía DNS interno dentro de la red compartida.
