Módulo 03

Imágenes y Dockerfile

Hasta ahora usaste imágenes que otros construyeron (nginx, ubuntu, alpine). Aquí aprendes a construir las tuyas.

03.1 Una imagen es una receta, no el plato

Analogía de cocina

Una imagen es como una receta escrita: una lista fija de pasos e ingredientes que no cambia. Un contenedor es el plato ya preparado a partir de esa receta —puedes cocinar (ejecutar) la misma receta diez veces y obtener diez platos (contenedores) independientes, pero la receta original nunca se altera. Por eso las imágenes son de solo lectura: modificar un contenedor en marcha no cambia la imagen de la que salió.

03.2 Capas: por qué Docker es tan eficiente

Una imagen no es un bloque monolítico: se construye como una pila de capas, cada una representando una instrucción del Dockerfile.

Analogía de las hojas de calco

Piensa en hojas de acetato transparentes apiladas una sobre otra, cada una con un dibujo distinto. Juntas forman la imagen completa, pero cada hoja sigue siendo un archivo independiente. Si cambias solo la hoja de arriba, no necesitas re-dibujar las de abajo. Docker hace lo mismo: si solo cambia tu código fuente pero no tus dependencias, Docker reutiliza (cachea) las capas de dependencias y solo reconstruye la capa que cambió. Por eso el orden de las instrucciones en el Dockerfile importa muchísimo para la velocidad del build.

03.3 Anatomía de un Dockerfile

Dockerfile
FROM node:20-alpine

WORKDIR /app

# Copiar SOLO el manifiesto de dependencias primero (aprovecha la caché de capas)
COPY package*.json ./
RUN npm install

# Recién ahora copiar el resto del código
COPY . .

EXPOSE 3000
ENV NODE_ENV=production

CMD ["node", "server.js"]
InstrucciónPara qué sirve
FROMImagen base sobre la que construyes. Siempre la primera línea.
WORKDIRDefine el directorio de trabajo dentro del contenedor (crea la carpeta si no existe).
COPYCopia archivos desde tu máquina hacia la imagen.
ADDComo COPY, pero además puede descomprimir tars y descargar URLs. Prefiere COPY salvo que necesites eso.
RUNEjecuta un comando durante el build y guarda el resultado como una capa nueva.
CMDComando por defecto al iniciar el contenedor. Se puede sobrescribir al hacer docker run.
ENTRYPOINTComo CMD, pero más difícil de sobrescribir — define el "ejecutable principal" del contenedor.
ENVDefine una variable de entorno disponible en build y en runtime.
ARGVariable disponible solo durante el build (no persiste en el contenedor final).
EXPOSEDocumenta qué puerto usa la app (no lo publica por sí solo, es informativo).
USERCambia el usuario con el que corren las siguientes instrucciones y el contenedor final.
CMD vs. ENTRYPOINT

Regla práctica: usa ENTRYPOINT para el programa fijo que el contenedor siempre debe ejecutar, y CMD para los argumentos por defecto de ese programa, que sí quieres que alguien pueda cambiar fácilmente.

03.4 Construir y etiquetar

bash
# Construir la imagen desde el Dockerfile en el directorio actual
docker build -t mi-app:1.0 .

# Etiquetar una imagen existente con otro nombre/versión
docker tag mi-app:1.0 usuario/mi-app:1.0

# Subirla a Docker Hub (requiere docker login primero)
docker push usuario/mi-app:1.0

El . al final de docker build es el contexto de build: la carpeta cuyos archivos están disponibles para las instrucciones COPY/ADD.

03.5 .dockerignore

Igual que .gitignore, evita que archivos innecesarios —o sensibles— entren al contexto de build y terminen dentro de la imagen.

03.6 Multi-stage builds

Para compilar tu app necesitas herramientas pesadas (compiladores, dependencias de desarrollo). Para correrla en producción, no. Un build multi-etapa te deja usar una imagen para compilar y otra, mucho más liviana, solo para ejecutar el resultado.

Analogía

Es como un taller de carpintería: usas máquinas grandes y ruidosas (sierras, lijadoras) para fabricar una silla, pero al final solo envías la silla terminada al cliente, no todo el taller. La etapa de "build" es el taller; la etapa final es solo el producto empacado.

Dockerfile
# --- Etapa 1: build (imagen pesada, con todo el toolchain) ---
FROM node:20 AS builder
WORKDIR /app
COPY . .
RUN npm install && npm run build

# --- Etapa 2: producción (imagen mínima, solo el resultado) ---
FROM nginx:alpine
COPY --from=builder /app/dist /usr/share/nginx/html
Resultado

La imagen final solo contiene nginx + los archivos compilados. Ni Node.js, ni node_modules, ni el código fuente terminan en la imagen de producción. Puede reducir el tamaño final de cientos de MB a unos pocos MB.
