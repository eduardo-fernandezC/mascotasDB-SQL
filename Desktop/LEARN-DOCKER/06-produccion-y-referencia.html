Módulo 06 · Último tramo

Producción y referencia rápida

La diferencia entre "sé usar Docker" y "puedo llevar esto a producción" está en un puñado de hábitos. Cierra con el cheat sheet completo para tenerlo siempre a mano.

06.1 Imágenes pequeñas, deliberadamente

Cada MB extra en tu imagen es más superficie de ataque, más tiempo de descarga y más tiempo de despliegue.

  • Prefiere bases alpine o distroless en vez de imágenes completas de Ubuntu/Debian cuando sea posible.
  • Usa multi-stage builds (visto en el módulo 03) para no cargar herramientas de compilación en producción.
  • Combina instrucciones RUN relacionadas en una sola línea para reducir capas innecesarias.
Dockerfile
# En vez de tres RUN separados, uno solo encadenado:
RUN apt-get update && \
    apt-get install -y curl && \
    rm -rf /var/lib/apt/lists/*

06.2 Nunca corras como root dentro del contenedor

Por defecto, los procesos dentro de un contenedor corren como root. Si un atacante logra escapar del aislamiento del contenedor, hereda esos privilegios en el host.

Dockerfile
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser

06.3 Nunca uses el tag :latest en producción

El problema

:latest es una etiqueta móvil — apunta a lo que sea que se publicó más recientemente, sin garantía de qué versión es. Un docker pull en un servidor puede traer código distinto al que probaste ayer, sin que nadie lo haya pedido explícitamente.

Usa versiones explícitas y, para trazabilidad total, el hash del commit o el digest de la imagen:

bash
docker run mi-app:2.4.1
# o, para inmutabilidad total, por digest de contenido:
docker run mi-app@sha256:a1b2c3...

06.4 Healthchecks

Le dicen a Docker (y a quien orqueste tus contenedores) si tu app está realmente respondiendo, no solo si el proceso sigue vivo.

Dockerfile
HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD curl -f http://localhost:3000/health || exit 1

06.5 Límites de recursos

Sin límites, un contenedor con una fuga de memoria puede consumir todo el host.

bash
docker run --memory=512m --cpus=1.5 mi-app

06.6 Secretos: nunca en el Dockerfile ni en ENV en texto plano

Error común

Un ENV DB_PASSWORD=secreto en el Dockerfile queda grabado permanentemente en la imagen y visible con docker history, aunque borres esa línea después. Usa inyección en runtime (variables de entorno pasadas al run/Compose, o un gestor de secretos) — nunca lo escribas dentro de la imagen.

06.7 Escaneo de vulnerabilidades

bash
# Docker Scout, integrado en el CLI moderno
docker scout cves mi-app:2.4.1

# Alternativa muy usada: Trivy
trivy image mi-app:2.4.1

06.8 Checklist antes de desplegar

  • Imagen base mínima (alpine/distroless) y multi-stage build aplicado.
  • Usuario no-root definido con USER.
  • Tag explícito, nunca :latest.
  • Healthcheck configurado.
  • Límites de CPU/memoria definidos.
  • Secretos inyectados en runtime, jamás horneados en la imagen.
  • .dockerignore excluyendo .git, .env y artefactos innecesarios.
  • Escaneo de vulnerabilidades corrido sobre la imagen final.

06.9 Cheat sheet completo

Referencia rápida de todo lo visto en la guía, agrupado por categoría.

Ciclo de vida

docker run [flags] imagenCrea y arranca un contenedor nuevo
docker start <id>Reinicia un contenedor detenido existente
docker stop <id>Detiene de forma ordenada
docker restart <id>Detiene e inicia de nuevo
docker kill <id>Detiene de inmediato, sin gracia
docker rm <id>Elimina un contenedor detenido
docker rm -f <id>Fuerza la eliminación aunque esté corriendo

Inspección

docker ps / ps -aContenedores corriendo / todos
docker logs -f <id>Logs en vivo
docker inspect <id>Metadata completa en JSON
docker statsUso de CPU/memoria en tiempo real
docker top <id>Procesos corriendo dentro del contenedor
docker exec -it <id> bashTerminal dentro de un contenedor activo
docker cp origen destinoCopia archivos host ↔ contenedor

Imágenes

docker imagesLista imágenes locales
docker pull imagenDescarga sin ejecutar
docker build -t nombre .Construye desde un Dockerfile
docker tag origen destinoRenombra/etiqueta
docker push imagenSube a un registro
docker rmi imagenElimina una imagen local
docker history imagenMuestra las capas y su tamaño

Volúmenes y redes

docker volume create/ls/rmGestión de volúmenes
docker network create/ls/inspectGestión de redes
-v origen:destinoMonta un volumen o bind mount
--network nombreConecta el contenedor a una red

Compose

docker compose up -dLevanta todos los servicios en segundo plano
docker compose down [-v]Detiene y elimina (con -v, borra volúmenes también)
docker compose logs -fLogs combinados de todos los servicios
docker compose exec servicio bashTerminal dentro de un servicio
docker compose buildReconstruye imágenes definidas con "build:"

Limpieza y sistema

docker system prune [-a]Limpia recursos sin usar
docker system dfEspacio en disco usado por Docker

06.10 Glosario

ImagenPlantilla de solo lectura de la que se crean contenedores
ContenedorInstancia en ejecución de una imagen
Registro (registry)Almacén de imágenes; Docker Hub es el más común
Daemon (dockerd)Proceso en segundo plano que gestiona todo el motor Docker
Capa (layer)Cada instrucción del Dockerfile genera una capa cacheable
VolumenMecanismo de persistencia de datos independiente del ciclo de vida del contenedor
OrquestaciónCoordinación de múltiples contenedores/hosts (Compose para un host, Kubernetes/Swarm para varios)
Siguiente paso natural

Cuando necesites correr contenedores en varios servidores a la vez, con autoescalado y recuperación automática ante fallos, el siguiente escalón es Kubernetes — pero todo lo que aprendiste aquí (imágenes, capas, redes, volúmenes) sigue siendo la base sobre la que se construye.
